# Nexus MVP Architecture

Status: **superseded by `MVP_ARCHITECTURE_V2.md`**
Retained for diffing only. Not authoritative.
Known defects are listed in `MVP_ARCHITECTURE_REVIEW.md`.

Stage: inception
Authority: none — see v2

Scope: the smallest coherent architecture that can execute one Task end to end
without violating any constitutional principle.

---

## 0. MVP Definition

One walking skeleton:

```
Capability declared in Nexus
→ Repository bootstrapped from Nexus
→ Task linked to Capability
→ Work Package generated by graph traversal
→ Execution Run dispatched through a Runtime Adapter
→ Pull Request opened on GitHub
→ Alignment check passes in CI
```

Everything not required by that path is postponed.

---

## 1. Bounded Contexts

Four core contexts, one supporting context, one anti-corruption boundary.

| Context | Authority over | Aggregates | Core? |
|---|---|---|---|
| Architecture | structure, governance | ArchitectureElement, Decision, Constraint | core |
| Work | intent, acceptance | WorkItem | core |
| Repository | implementation projections | Repository | core |
| Execution | execution contract, run lifecycle | WorkPackage, ExecutionRun, AgentRole | core |
| Alignment | drift detection | (none — query-only) | supporting |
| Runtime Integration | runtime translation | AdapterRegistration | ACL |

### Boundary rules

- Architecture, Work and Repository never reference each other by object.
  They reference each other **only by stable ID**.
- Execution is a **downstream** context. It reads the other three and owns
  the assembled contract. Nothing upstream depends on Execution.
- Runtime Integration is the **only** context permitted to know that a
  runtime is Claude, OpenAI or anything else.
- Alignment owns no state. It is a set of named queries plus a verify endpoint.

### Context mapping

```
Architecture ──published language (IDs)──┐
Work ────────published language (IDs)────┼──> Execution ──port──> Runtime Integration ──> Agent Runtime
Repository ──published language (IDs)────┘
                                          └──> Alignment (read-only across all)
```

Physical enforcement: one Postgres schema per context
(`architecture`, `work`, `repo`, `execution`, `runtime`).
Cross-schema foreign keys are permitted only on ID columns and only in the
downstream direction.

## 2. Aggregate Roots

Six aggregate roots. Deliberately few.

### 2.1 `ArchitectureElement` (Architecture)

The taxonomy Product → Domain → Subsystem → Component → Capability is a
homogeneous containment tree. It is modelled as **one** aggregate with a `kind`
discriminator and a `parentId`, because the Graph Model requires node
uniformity and per-kind aggregates would add five lifecycles with identical
invariants.

Owns:
- identity, kind, name, status
- containment link to parent
- outgoing `dependsOn` edges (Component only)

Invariants:
- `kind` + `parent.kind` must appear in the legal-containment table
- exactly one parent, except `product` which has none
- no self-dependency
- `dependsOn` permitted only between `component` elements
- status transitions: `active → deprecated → retired`; never deleted

Deferred to Alignment (not an aggregate invariant): dependency acyclicity.

### 2.2 `Decision` (Architecture)

ADR as first-class node. Owns id, title, status, statement, and the set of
element IDs it governs.

### 2.3 `Constraint` (Architecture)

Small named catalogue (`con.backward-compatible`). A Constraint is attached to
elements and **inherited down the containment tree**. Enforcement is not
modelled in MVP — constraints are propagated into Work Packages as
obligations, and verified by humans at PR review.

### 2.4 `WorkItem` (Work)

Initiative → Epic → Feature → Task, same typed-tree argument as 2.1.

Owns:
- identity, kind, title, status, parent link
- `AcceptanceCriterion` child entities (Task only)
- `affects` links to Capability IDs (Task only)

Invariants:
- legal containment by kind
- **no orphan tasks**: a Task may not leave `draft` with zero Capability links
- a Task may not leave `draft` with zero AcceptanceCriteria
- AcceptanceCriteria exist only inside a Task; they are never reparented

### 2.5 `Repository` (Repository)

Owns:
- identity, name, VCS provider reference, default branch
- `implements` mappings to Component IDs
- bootstrap state
- file anchors (curated path-glob → element mappings)

Invariants:
- at least one `implements` mapping before state `mapped`
- may map only elements of kind `component`
- a Repository ID is minted by Nexus **before** provisioning

### 2.6 `WorkPackage` (Execution)

**Immutable.** Insert-only. Identified by a monotonic sequence and carrying a
canonical content hash. Has no mutable status field at all — its lifecycle is
derived from the ExecutionRuns that reference it.

### 2.7 `ExecutionRun` (Execution)

One attempt of one WorkPackage under one AgentRole. Owns a runtime-neutral
state machine and an opaque adapter identifier. Contains no runtime concepts.

### Not aggregate roots

- `File` — a projection, high churn, machine-maintained. Postponed entirely;
  MVP uses curated `FileAnchor` values inside the Repository aggregate.
- `AgentRole` — a Nexus-owned reference catalogue, effectively immutable data.
- `AdapterRegistration` — lives outside the core model.

## 3. Domain Model

### 3.1 Ubiquitous language

| Term | Definition |
|---|---|
| ArchitectureElement | A node in the architecture taxonomy |
| Capability | The unit of behaviour Work attaches to; the pivot of the graph |
| Dependency | A directed `dependsOn` relation between Components |
| Decision | An architectural decision governing one or more elements |
| Constraint | A named, inheritable obligation on elements |
| WorkItem | A node in the work taxonomy |
| AcceptanceCriterion | A verifiable condition owned by a Task |
| Repository | An implementation projection of one or more Components |
| ImplementationMapping | `Repository implements Component` |
| FileAnchor | A curated glob binding repository paths to an element |
| WorkPackage | The immutable, runtime-neutral execution contract |
| AgentRole | A Nexus-owned logical role an execution fulfils |
| ExecutionRun | One attempt to fulfil a WorkPackage under a Role |
| RuntimeAdapter | A translator between WorkPackage and a concrete runtime |
| Alignment | Agreement between Nexus state and repository projections |
| Drift | Detected disagreement |

### 3.2 Legal containment

| Parent kind | Child kind |
|---|---|
| (none) | product |
| product | domain |
| domain | subsystem |
| subsystem | component |
| component | capability |
| (none) | initiative |
| initiative | epic |
| epic | feature |
| feature | task |

This table is data, not code. New taxonomy levels are a data migration.

### 3.3 Relations (canonical)

```
Product        contains      Domain
Domain         contains      Subsystem
Subsystem      contains      Component
Component      provides      Capability
Component      dependsOn     Component
Repository     implements    Component
Task           affects       Capability
Task           implementedIn Repository        (optional override)
Repository     anchors       ArchitectureElement
Decision       governs       ArchitectureElement
Constraint     constrains    ArchitectureElement
Element        supersededBy  Element
```

`Task implementedIn Repository` is normally **derived**
(`task → capability → component → repository`). The explicit edge exists only
to disambiguate when a Component is implemented by more than one Repository.

### 3.4 Agent roles are domain, models are not

`AGENT_RUNTIME_MODEL.md` places roles in Nexus. Therefore:

- `role.task-analyst`, `role.context-navigator`, `role.code-locator`,
  `role.implementer`, `role.knowledge-maintainer`, `role.consistency-auditor`
  are **core domain identifiers**.
- The binding from a role to a model, prompt or SDK lives entirely in
  Runtime Integration.

This is the single most important seam for runtime independence.

## 4. Stable ID Strategy

### 4.1 Two ID classes

**Authored IDs** — human-meaningful, slug-based, immutable, referenced across
contexts and inside repositories.

```
<prefix>.<slug>
slug := [a-z0-9]+(-[a-z0-9]+)*
```

| Prefix | Entity |
|---|---|
| `prod.` | Product |
| `dom.` | Domain |
| `subsys.` | Subsystem |
| `comp.` | Component |
| `cap.` | Capability |
| `repo.` | Repository |
| `init.` | Initiative |
| `epic.` | Epic |
| `feat.` | Feature |
| `task.` | Task |
| `ac.` | AcceptanceCriterion |
| `adr.` | Decision |
| `con.` | Constraint |
| `role.` | AgentRole |
| `wpp.` | WorkPackage profile |

**Generated IDs** — opaque, machine-minted, never authored.

| Form | Entity |
|---|---|
| `wp.<seq>` | WorkPackage (display form `WP-123`) |
| `run.<ulid>` | ExecutionRun |

Internal-only entities (FileAnchor, mapping rows) use surrogate UUIDs and get
**no** public identifier. Only entities referenced across a context boundary
earn a stable ID.

### 4.2 Rules

1. IDs are globally unique on the full string, including prefix.
2. IDs are immutable. `name` is mutable; `id` never is.
3. Slugs are flat, not path-qualified. Uniqueness is a naming discipline
   enforced at creation, which keeps deterministic retrieval a single lookup.
4. Nothing is deleted. `status` moves `active → deprecated → retired`.
5. Replacement is modelled by `supersededBy`, not by ID reuse.
6. A retired ID is never reissued.
7. Nexus mints every ID. GitHub, Jira and runtimes never do.

### 4.3 Postponed

Path-qualified slugs, ID aliasing, merge/split of elements, multi-tenant ID
namespacing. All are additive; none require reissuing existing IDs.

## 5. Relational Schema

Postgres is the system of truth. One schema per bounded context.

### 5.1 `architecture`

```sql
create table architecture.element (
  id           text primary key,
  kind         text not null check (kind in
                 ('product','domain','subsystem','component','capability')),
  parent_id    text references architecture.element(id),
  name         text not null,
  status       text not null default 'active'
                 check (status in ('active','deprecated','retired')),
  superseded_by text references architecture.element(id),
  created_at   timestamptz not null default now(),
  updated_at   timestamptz not null default now()
);

create table architecture.legal_containment (
  parent_kind text,
  child_kind  text,
  primary key (parent_kind, child_kind)
);
-- trigger on element enforces (parent.kind, kind) ∈ legal_containment

create table architecture.element_dependency (
  from_id text not null references architecture.element(id),
  to_id   text not null references architecture.element(id),
  primary key (from_id, to_id),
  check (from_id <> to_id)
);
-- trigger enforces both endpoints are kind='component'

create table architecture.decision (
  id        text primary key,
  title     text not null,
  status    text not null default 'accepted'
              check (status in ('proposed','accepted','superseded')),
  statement text not null
);

create table architecture.decision_scope (
  decision_id text references architecture.decision(id),
  element_id  text references architecture.element(id),
  primary key (decision_id, element_id)
);

create table architecture.constraint_def (
  id        text primary key,
  title     text not null,
  statement text not null
);

create table architecture.element_constraint (
  element_id    text references architecture.element(id),
  constraint_id text references architecture.constraint_def(id),
  primary key (element_id, constraint_id)
);
```

### 5.2 `work`

```sql
create table work.work_item (
  id         text primary key,
  kind       text not null check (kind in
               ('initiative','epic','feature','task')),
  parent_id  text references work.work_item(id),
  title      text not null,
  status     text not null default 'draft'
               check (status in ('draft','ready','in_progress','done','cancelled')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
-- trigger enforces legal containment by kind

create table work.work_item_capability (       -- Task affects Capability
  work_item_id  text references work.work_item(id),
  capability_id text not null,                 -- architecture.element(id)
  primary key (work_item_id, capability_id)
);

create table work.acceptance_criterion (
  id           text primary key,
  work_item_id text not null references work.work_item(id),
  statement    text not null,
  ordinal      int not null,
  unique (work_item_id, ordinal)
);
```

`capability_id` is intentionally **not** a cross-schema FK. Work depends on
Architecture through published IDs only; referential validity is asserted by
Alignment, which keeps the two contexts independently deployable.

The no-orphan-task invariant is enforced in the aggregate on the
`draft → ready` transition, and re-verified continuously by
`alignment.orphan_tasks`.

### 5.3 `repo`

```sql
create table repo.repository (
  id              text primary key,
  name            text not null,
  provider        text not null,            -- 'github'
  provider_ref    text,                     -- owner/name, null until provisioned
  default_branch  text not null default 'main',
  bootstrap_state text not null default 'declared'
                    check (bootstrap_state in
                      ('declared','provisioned','mapped','bootstrapped','active')),
  template_version text,
  created_at      timestamptz not null default now()
);

create table repo.repository_component (       -- Repository implements Component
  repository_id text references repo.repository(id),
  component_id  text not null,
  primary key (repository_id, component_id)
);

create table repo.file_anchor (
  id            uuid primary key default gen_random_uuid(),
  repository_id text not null references repo.repository(id),
  path_glob     text not null,
  element_id    text not null,
  note          text
);
```

### 5.4 `execution`

```sql
create table execution.agent_role (
  id      text primary key,
  name    text not null,
  purpose text not null
);

create table execution.work_package (
  id           text primary key,             -- wp.<seq>
  seq          bigint not null unique,
  task_id      text not null,
  profile_id   text not null,                -- wpp.implementation
  content_hash text not null,
  payload      jsonb not null,
  schema_version text not null,
  created_at   timestamptz not null default now(),
  unique (task_id, profile_id, content_hash)
);
-- insert-only; no UPDATE grant

create table execution.execution_run (
  id              text primary key,          -- run.<ulid>
  work_package_id text not null references execution.work_package(id),
  role_id         text not null references execution.agent_role(id),
  adapter_id      text not null,             -- opaque; no runtime semantics
  state           text not null default 'pending'
                    check (state in ('pending','dispatched','running',
                                     'produced','completed','failed','cancelled')),
  artifact_ref    text,                      -- PR URL
  started_at      timestamptz,
  ended_at        timestamptz
);

create table execution.run_event (
  id       bigserial primary key,
  run_id   text not null references execution.execution_run(id),
  kind     text not null,                    -- runtime-neutral event kind
  payload  jsonb,
  at       timestamptz not null default now()
);
```

`work_package.payload` is immutable and canonical. `adapter_id` is an opaque
port identifier — Execution stores it, never interprets it.

### 5.5 `runtime` (Runtime Integration, non-core)

```sql
create table runtime.adapter_registration (
  id           text primary key,             -- 'claude-sdk'
  display_name text not null,
  config       jsonb not null,               -- model, prompt template, tool policy
  enabled      boolean not null default true
);

create table runtime.hint_file_template (
  adapter_id text references runtime.adapter_registration(id),
  file_path  text not null,                  -- 'CLAUDE.md', 'AGENTS.md'
  template   text not null,
  primary key (adapter_id, file_path)
);
```

Every runtime-specific string in the platform lives here. `CLAUDE.md` is a
template row in a supporting context, not a domain concept.

## 6. Graph Schema

### 6.1 MVP decision: no graph database

The graph is the **canonical relationship model**, not necessarily a separate
store. In MVP the graph is a set of named recursive-CTE views over Postgres.
Node labels, edge types and traversal names are defined now so that swapping in
a graph database later is a substitution, not a redesign.

### 6.2 Node labels

`Product`, `Domain`, `Subsystem`, `Component`, `Capability`,
`Initiative`, `Epic`, `Feature`, `Task`,
`Repository`, `Decision`, `Constraint`

Node key: the stable ID. Node properties: `name`, `status`.

`AcceptanceCriterion`, `FileAnchor`, `WorkPackage` and `ExecutionRun` are
**not** graph nodes in MVP. They are payload reached by ID from a node.

### 6.3 Edge types

| Edge | From → To |
|---|---|
| `CONTAINS` | Product→Domain→Subsystem→Component, Initiative→Epic→Feature→Task |
| `PROVIDES` | Component → Capability |
| `DEPENDS_ON` | Component → Component |
| `IMPLEMENTS` | Repository → Component |
| `AFFECTS` | Task → Capability |
| `IMPLEMENTED_IN` | Task → Repository (override only) |
| `ANCHORS` | Repository → ArchitectureElement |
| `GOVERNS` | Decision → ArchitectureElement |
| `CONSTRAINS` | Constraint → ArchitectureElement |
| `SUPERSEDED_BY` | Element → Element |

### 6.4 Named traversals

These names are the retrieval contract. MCP tools and the Context Builder call
only these — never ad-hoc queries, never document search.

| Traversal | Path |
|---|---|
| `implementationPath(task)` | Task→AFFECTS→Capability←PROVIDES←Component←IMPLEMENTS←Repository |
| `ancestry(element)` | element →CONTAINS*→ root |
| `capabilitiesOf(component)` | Component→PROVIDES→Capability |
| `impactOf(component, depth)` | Component→DEPENDS_ON{1..depth}→Component |
| `governanceOf(element)` | ancestry(element) ←GOVERNS/CONSTRAINS← Decision/Constraint |
| `localSubgraph(component)` | Component + capabilities + direct dependencies |
| `orphanTasks()` | Task with no AFFECTS |
| `unmappedComponents()` | Component with no inbound IMPLEMENTS |
| `danglingReferences()` | edges whose endpoint is missing or `retired` |

The last three are the Alignment context's entire surface.

### 6.5 Inheritance semantics

Constraints and Decisions are inherited **down** `CONTAINS`. A Decision on
`dom.billing` governs every Component beneath it. Resolution is
nearest-ancestor-wins, and the resolved set is materialised into the Work
Package so the agent never has to re-derive it.

## 7. MCP Specifications

### 7.1 Role of MCP

- The Work Package delivers the **minimum** context required to start.
- MCP delivers **deterministic expansion** during a run.
- MCPs are read views over Postgres. They cache nothing. They are not systems
  of truth.
- No free-text or semantic search. Every tool takes IDs and returns structure.

Three servers, matching the Constitution.

### 7.2 Architecture MCP

| Tool | Input | Output |
|---|---|---|
| `architecture.get_element` | `id` | kind, name, status, parentId, childIds |
| `architecture.get_ancestry` | `id` | ordered ancestor IDs with kinds |
| `architecture.list_capabilities` | `componentId` | capability IDs + names |
| `architecture.get_dependencies` | `componentId`, `direction`, `depth≤3` | component IDs by distance |
| `architecture.get_governance` | `elementId` | resolved decisions + constraints |

### 7.3 Work MCP

Read-only in MVP.

| Tool | Input | Output |
|---|---|---|
| `work.get_item` | `id` | kind, title, status, parentId, childIds |
| `work.get_task_context` | `taskId` | title, ACs, affected capability IDs, feature ID |
| `work.list_tasks` | `featureId`, `status?` | task IDs |

### 7.4 Repository MCP

| Tool | Input | Output |
|---|---|---|
| `repo.get_repository` | `id` | provider ref, branch, implemented component IDs |
| `repo.list_for_component` | `componentId` | repository IDs |
| `repo.get_anchors` | `repositoryId`, `elementId?` | path globs + element IDs |
| `repo.get_bootstrap_manifest` | `repositoryId` | expected generated files + hashes |

### 7.5 Access model

Every MCP session is authorised by a **run-scoped grant** issued when an
ExecutionRun is dispatched:

```
grant = {
  runId,
  workPackageId,
  allowedElementIds,      -- WP subgraph + impactOf(depth 1)
  allowedRepositoryIds,
  expiresAt
}
```

A tool call outside the grant is refused. Authorisation is therefore a
property of the graph, not of a user role table — which removes the need for
RBAC in MVP and makes agent blast radius provably bounded.

### 7.6 Postponed

Write tools (`architecture.propose_element`, `repo.register_anchor`,
`work.report_progress`), subscriptions, pagination beyond a fixed cap,
a fourth Execution MCP.

## 8. Repository Bootstrap Process

### 8.1 State machine

```
declared → provisioned → mapped → bootstrapped → active
```

### 8.2 Steps

| # | Step | Precondition | Effect |
|---|---|---|---|
| 1 | Component exists | `comp.*` is `active` | — |
| 2 | Declare Repository | — | Nexus mints `repo.<slug>`; state `declared` |
| 3 | Provision | — | `VcsProvider.create()`; store `provider_ref`; state `provisioned` |
| 4 | Register mapping | ≥1 component | `IMPLEMENTS` edge; state `mapped` |
| 5 | Generate projection | mapped | files rendered; branch `nexus/bootstrap`; PR opened; state `bootstrapped` |
| 6 | Human merges PR | CI green | state `active` |

Repositories are never created by hand. `VcsProvider` is a port; GitHub is one
adapter.

### 8.3 Generated artifacts

| File | Content | Authority |
|---|---|---|
| `.nexus/repository.json` | repo ID, component IDs, Nexus base URL, schema version, snapshot hash | projection |
| `.nexus/architecture.snapshot.json` | `localSubgraph(component)` | projection |
| `.github/workflows/nexus-alignment.yml` | drift check job | projection |
| `CLAUDE.md`, `AGENTS.md` | runtime hint files rendered from `runtime.hint_file_template` | projection |

Every generated file carries a `nexus:generated` header and is listed in the
bootstrap manifest. None of them is authoritative. Nothing in a repository may
introduce an element, capability or mapping that does not already exist in
Nexus — that is the guardrail that keeps architecture from originating in
repositories.

### 8.4 Generation is a pure function

```
render(repository, localSubgraph, templateVersion) → files
```

Deterministic and idempotent. Therefore **drift detection is regeneration plus
diff** — no separate drift model, no separate parser.

### 8.5 Alignment check (CI)

The workflow posts `.nexus/repository.json` to `POST /alignment/verify`.

Fails when:
- repository ID unknown
- `implements` mapping missing or contradicted
- a referenced element ID does not exist
- a referenced element is `retired`
- a mapped component has no capabilities

Warns when:
- snapshot hash is stale (Nexus moved ahead)
- generated files differ from a fresh render

Postponed: file-anchor verification, dependency-cycle detection, capability
coverage by tests.

## 9. Work Package Generation Process

### 9.1 Contract

```
buildWorkPackage(taskId, profileId) → WorkPackage
```

Pure with respect to graph state. Same graph + same task + same profile ⇒ same
content hash ⇒ the existing immutable WorkPackage is returned. Generation is
idempotent and auditable.

MVP has exactly one profile: `wpp.implementation`.

### 9.2 Pipeline

1. **Gate.** Task exists, status `ready`, ≥1 `AFFECTS`, ≥1 AcceptanceCriterion.
   Fail closed.
2. **Traverse.** `implementationPath(task)` → capabilities, components,
   repositories.
3. **Anchor.** For each repository, `get_anchors` filtered to the resolved
   elements → candidate file globs.
4. **Govern.** `governanceOf` each resolved element → decisions + constraints,
   nearest-ancestor-wins.
5. **Frame.** Parent Feature ID and title only. No prose, no descriptions
   inherited upward.
6. **Bound.** `impactOf` depth **0** in MVP — only directly implementing
   components are included. Widening the depth is a profile setting later.
7. **Canonicalise.** Sort keys, sort arrays, serialise, hash.
8. **Persist.** Insert-only. Emit `WorkPackageIssued`.

### 9.3 Payload

Exactly `WORK_PACKAGE_SPEC.md`, plus `schemaVersion` and `profile`.

```yaml
id: WP-123
schemaVersion: 1
profile: wpp.implementation
task: task.invoice-discount-validation
feature: feat.invoice-discounts
capabilities: [cap.invoice-discount]
components: [comp.invoice-service]
repositories: [repo.billing-service]
files: [InvoiceService.java]
constraints: [con.backward-compatible]
acceptanceCriteria: [ac.discount-applied, ac.existing-behaviour-unchanged]
decisions: [adr.discount-strategy-v1]
```

IDs, not prose. Statements for `acceptanceCriteria`, `constraints` and
`decisions` are fetched through MCP when the agent needs them — which keeps the
package small and keeps the platform the single source of the text.

### 9.4 Postponed

Token budgeting, relevance ranking, multi-task packages, dependency-closure
context, additional profiles (audit, knowledge maintenance, review).
Explicitly excluded: embedding or vector retrieval — retrieval stays
deterministic.

## 10. Agent Orchestrator Architecture

### 10.1 Layering

```
Execution context (core, runtime-agnostic)
  ├─ Role Registry
  ├─ Context Builder            (§9)
  ├─ Orchestrator               (run lifecycle, policy, grants)
  └─ AgentRuntimeAdapter        (port)
        │
Runtime Integration context (ACL)
  └─ Claude SDK Adapter         (the only runtime-aware code in the system)
        │
Agent Runtime
```

### 10.2 The port

```
interface AgentRuntimeAdapter {
  id: AdapterId
  capabilities(): AdapterCapabilities        // supported roles, streaming, tools
  start(run, workPackage, mcpGrant): AdapterHandle
  events(handle): stream<RunEvent>
  cancel(handle): void
}
```

Runtime-neutral event vocabulary — the full set:

`RunStarted`, `ContextRequested`, `ArtifactProduced`, `RunFailed`,
`RunCompleted`

No messages, no tokens, no tool-call shapes, no model names cross this
boundary. Anything a runtime emits that does not map to these five is the
adapter's problem.

### 10.3 Run lifecycle

```
pending → dispatched → running → produced → completed
                    ↘ failed
                    ↘ cancelled
```

The Orchestrator:
1. resolves `(workPackage, role)`
2. selects an enabled adapter that declares support for the role
3. issues the run-scoped MCP grant (§7.5)
4. dispatches, records `RunEvent`s, drives the state machine
5. records `artifact_ref` on `ArtifactProduced`

### 10.4 Output path

Agents do not write to Nexus. An ExecutionRun produces a **branch and a pull
request**. GitHub remains merge governance; a human merges. Knowledge updates
flowing back into Nexus are postponed to iteration 3.

This single constraint removes the need for agent write authorisation,
optimistic concurrency on the graph, and rollback machinery in MVP.

### 10.5 Roles in MVP

| Role | MVP treatment |
|---|---|
| `role.implementer` | **orchestrated** |
| `role.task-analyst` | collapses into the §9.1 validation gate |
| `role.context-navigator` | collapses into MCP — the agent navigates itself |
| `role.code-locator` | collapses into file anchors + Repository MCP |
| `role.knowledge-maintainer` | registered, not orchestrated |
| `role.consistency-auditor` | replaced by the Alignment check (§8.5) |

One role, one run, no choreography. Multi-agent orchestration is iteration 3.

### 10.6 Claude SDK Adapter

Translates only:
- WorkPackage + role → system prompt, from `runtime.adapter_registration.config`
- MCP grant → MCP server configuration and tool allowlist
- SDK events → the five `RunEvent` kinds
- final state → branch push + PR via `VcsProvider`

Adding a second runtime means adding one row and one class. The core model does
not change. That is the test of whether this design held.

---

## 11. Where Complexity Is Postponed

| Postponed | Iteration | Why it is safe to defer |
|---|---|---|
| Graph database | 2 | Graph schema is defined; CTEs are a substitutable implementation |
| File-level graph (`Repository contains File`) | 3 | Curated anchors cover WP file hints |
| MCP write tools | 2 | PR-only output path needs no agent writes |
| Multi-agent choreography | 3 | One role proves the port |
| Additional runtime adapters | 2 | Port and event vocabulary already fixed |
| Constraint enforcement | 3 | Constraints propagate as obligations; PR review verifies |
| Dependency-cycle detection | 2 | Alignment query, not an aggregate invariant |
| Token budgeting / relevance ranking | 3 | Depth-0 traversal keeps packages small |
| Additional WP profiles | 2 | `profile` field already in the payload |
| RBAC / multi-tenancy | 2 | Run-scoped graph grants bound blast radius |
| Event bus / async messaging | 2 | In-process domain events + outbox table |
| Per-kind architecture aggregates | 2 | Only needed if kind-specific invariants appear |
| Path-qualified slugs, ID aliasing | 3 | Purely additive to §4 |
| Element merge / split | later | `supersededBy` covers replacement |
| Architecture editing UI | 2 | YAML import + REST is enough to seed |

### Deliberately never

- Vendor concepts in the core domain model
- Architecture originating in repositories
- Document or semantic search as a retrieval path
- Chat as a workflow surface
