# Nexus MVP Architecture — v2

Status: proposed
Stage: inception
Supersedes: `MVP_ARCHITECTURE.md` (v1)
Authority: subordinate to `NEXUS_CONSTITUTION.md`
Incorporates: `MVP_ARCHITECTURE_REVIEW.md` recommendations R1–R11

Scope: the smallest coherent architecture that can execute one Task end to end,
**and evolve its own architecture**, without violating any constitutional
principle.

This document is self-contained. It replaces v1 rather than amending it.
Section 17 maps every v1 change for anyone diffing.

---

## 0. MVP Definition

One walking skeleton, now with a closed loop:

```
Capability declared in Nexus
→ Repository bootstrapped from Nexus
→ Task linked to Capability
→ Work Package generated by graph traversal
→ Execution Run dispatched through a Runtime Adapter
→ Pull Request opened on GitHub
→ Alignment check passes in CI
```

Plus the loop that v1 was missing:

```
Task requires architecture that does not exist
→ Run blocks, or the generation gate refuses
→ Architecture Change Proposal drafted
→ Human approves in Nexus
→ Elements minted, succession recorded, repository declared if needed
→ Task unblocked
```

Everything not required by those two paths is postponed (§15).

## 1. Governing Rules

Four rules cut across every section. They are stated once, here, and referenced
throughout.

### R-1 — Every agent write is a proposal

> Nothing an agent produces becomes platform truth without human approval.

Agents report; they do not write. In the MVP the only agent-originated change
to platform state is a **draft** `ArchitectureChangeProposal`, and even that is
written by the platform in response to a reported `RunBlocked` event — the
runtime never holds a write credential.

This is a permanent constraint, not an MVP simplification. When MCP write
tools arrive (iteration 2) they may create draft proposals or append
observations. They may never mutate an element, a mapping or a work item
directly.

This extends to workflow-state classification, not only graph writes: a
`RunEvent`'s kind and reason are determined by Nexus from the adapter's
reported observations, not asserted directly by agent-authored text.
Where Nexus has not yet built a deterministic classifier for a given
observation, an agent-reported signal may stand in — but it is
provisional evidence, not authority, and is expected to be replaced as
soon as a deterministic classifier is evidenced to be buildable. (Added
after the Architecture Review between Iterations 8 and 9 — see
`docs/PROJECT_KNOWLEDGE.md` and `docs/history/iteration-9/SCOPE.md`.)

### R-2 — Containment is structure; provision is behaviour

> `parent_id` means `CONTAINS` and nothing else.

Capability is contained by Subsystem and *provided* by one or more Components
(§4.2). No relation other than containment is ever stored in `parent_id`.

### R-3 — The cross-context foreign key rule

> A cross-context foreign key is **required** when all three hold:
> 1. the reference is **live** (a current invariant), not **historical**;
> 2. it points along a declared dependency direction (§2.3);
> 3. both schemas are in one deployable.
>
> It is **forbidden**, unconditionally, across the Runtime Integration
> boundary.
>
> Every *live* cross-context reference that is not a foreign key must be
> compensated by a named Alignment query (§8.5).

### R-4 — Identifiers are immutable; change is succession

> Nothing is renamed into a new identity, nothing is deleted, nothing is
> reused.

`name` is mutable, so renaming is a non-event. Structural change is expressed
by minting new IDs, retiring old ones, and recording `element_succession`
edges that retrieval can traverse forward (§6.4).

## 2. Bounded Contexts

Four core contexts, one supporting context, one anti-corruption boundary.

| Context | Authority over | Aggregate roots | Core? |
|---|---|---|---|
| Architecture | structure, governance, **architecture change** | ArchitectureElement, Decision, Constraint, **ArchitectureChangeProposal** | core |
| Work | intent, acceptance | WorkItem | core |
| Repository | implementation projections | Repository | core |
| Execution | execution contract, run lifecycle | WorkPackage, **WorkPackageProfile**, ExecutionRun | core |
| Alignment | drift detection | (none — query-only) | supporting |
| Runtime Integration | runtime translation, **AgentRole vocabulary** | AdapterRegistration | ACL |

### 2.1 Boundary rules

- Architecture, Work and Repository reference each other **only by stable ID**,
  never by object.
- Execution is a **downstream** context. Nothing upstream depends on it.
- Runtime Integration is the **only** context permitted to know that a runtime
  is Claude, OpenAI or anything else. It holds the `role.*` vocabulary.
- Alignment owns no state: named queries plus one verify endpoint.

### 2.2 Cross-context writes go through domain events

A context writes only its own aggregates. Where a change in one context must
affect another, an in-process domain event carries it and the owning context's
policy applies it.

| Event | Raised by | Handled by | Effect |
|---|---|---|---|
| `RunBlocked` | Execution | Architecture | draft proposal created |
| `RunBlocked` | Execution | Work | Task status → `blocked` |
| `ProposalApplied` | Architecture | Work | blocked Tasks released for re-gating |
| `ProposalApplied` | Architecture | Repository | Repository declared for each minted Component flagged `requires_repository` |
| `RepositoryActivated` | Repository | Work | Tasks awaiting a repository re-gated |

This is why Execution never writes to `work.work_item` even though §2.3 permits
it to read there.

### 2.3 Declared dependency directions

```
Work        → Architecture
Work        → Repository      (override edge only, §4.3)
Repository  → Architecture
Execution   → Architecture | Work | Repository
Alignment   → all (read-only)
Runtime Integration → Execution   (inbound port only; never referenced back)
```

Any reference against these arrows is a design error, not a schema detail.

### 2.4 Context map

```
Architecture ──published language (IDs)──┐
Work ────────published language (IDs)────┼──> Execution ──port──> Runtime Integration ──> Agent Runtime
Repository ──published language (IDs)────┘        │
        ▲                                          │ RunBlocked
        └───────── domain events ◀─────────────────┘
                                          └──> Alignment (read-only across all)
```

Physical enforcement: one Postgres schema per context — `architecture`, `work`,
`repo`, `execution`, `runtime`. Cross-schema foreign keys exist only where R-3
requires them.

## 3. Aggregate Roots

Eight aggregate roots.

### 3.1 `ArchitectureElement` (Architecture)

The containment tree Product → Domain → Subsystem → {Component, Capability} is
modelled as one aggregate with a `kind` discriminator and a `parentId`, because
the Graph Model requires node uniformity and per-kind aggregates would add
lifecycles with identical invariants.

Owns:
- identity, kind, name, status
- containment link to parent (`CONTAINS` only — R-2)
- outgoing `dependsOn` edges (Component only)
- outgoing `provides` edges (Component only)

Invariants:
- `(parent.kind, kind)` must appear in the legal-containment table
- exactly one parent, except `product`, which has none
- `dependsOn` permitted only between `component` elements; no self-dependency
- `provides` permitted only from `component` to `capability`
- at most one **primary** provider per capability
- status transitions `active → deprecated → retired`; never deleted
- retirement is refused while live inbound references exist, unless the same
  proposal supplies succession (§5.6)

Deferred to Alignment: dependency acyclicity.

### 3.2 `ArchitectureChangeProposal` (Architecture) — new in v2

The unit of governed architecture change. Owns an ordered list of
`ArchitectureOperation` child entities and a lifecycle. Has no effect until
approved.

Invariants:
- operations are ordered and applied atomically
- a `create` operation must name a legal parent for its kind
- a `retire` operation must target an `active` or `deprecated` element
- transition to `applied` is permitted only from `approved`
- `approved_by` must be a human principal
- application is transactional: mint, retire, and succession in one commit

### 3.3 `Decision` (Architecture)

ADR as a first-class node. Owns id, title, status, statement, and the element
IDs it governs.

### 3.4 `Constraint` (Architecture)

A small named catalogue (`con.backward-compatible`), attached to elements and
inherited down containment. Enforcement is not modelled; constraints propagate
into Work Packages as obligations and are verified at PR review.

### 3.5 `WorkItem` (Work)

Initiative → Epic → Feature → Task, one aggregate, same typed-tree argument as
§3.1. The four work kinds genuinely share one lifecycle.

Owns:
- identity, kind, title, status, parent link
- `AcceptanceCriterion` child entities (Task only)
- `affects` links to Capability IDs (Task only)
- `implementedIn` repository overrides (Task only, §4.3)
- the blocking link to a proposal, when blocked

Invariants:
- legal containment by kind
- **no orphan tasks**: a Task may not leave `draft` with zero Capability links
- a Task may not leave `draft` with zero AcceptanceCriteria
- AcceptanceCriteria exist only inside a Task; they are never reparented
- a Task in `blocked` names the proposal blocking it

### 3.6 `Repository` (Repository)

Owns identity, VCS provider reference, default branch, `implements` mappings to
Component IDs (with a primary flag), bootstrap state, and — pending §13 —
file anchors.

Invariants:
- at least one `implements` mapping before state `mapped`
- may map only elements of kind `component`
- at most one primary repository per component
- the Repository ID is minted by Nexus **before** provisioning

### 3.7 `WorkPackageProfile` (Execution) — promoted in v2

Determines what context gets constructed: traversal depth, provider fan-out,
governance resolution. Context construction is explicitly platform-owned, which
is what makes this core.

### 3.8 `WorkPackage` (Execution)

**Immutable.** Insert-only, identified by a monotonic sequence, carrying a
canonical content hash. No mutable status field at all — its lifecycle is
derived from the ExecutionRuns that reference it.

### 3.9 `ExecutionRun` (Execution)

One attempt at one WorkPackage. Owns a runtime-neutral state machine, an opaque
adapter identifier and an opaque adapter role reference. Contains no runtime
concepts.

### 3.10 Not aggregate roots

- `File` — a projection, high churn. See §13.
- `AgentRole` — a **Runtime Integration** vocabulary, not core (§4.4).
- `AdapterRegistration` — outside the core model.
- `Observation` — postponed (§15); the designated future channel for
  agent-reported facts under R-1.

## 4. Domain Model

### 4.1 Ubiquitous language

| Term | Definition |
|---|---|
| ArchitectureElement | A node in the architecture containment tree |
| Capability | The unit of behaviour Work attaches to; the graph's join point |
| Provision | `Component provides Capability` — mutable, many-to-many |
| Dependency | A directed `dependsOn` relation between Components |
| Succession | `predecessor supersededBy successor`, recorded by a proposal |
| ArchitectureChangeProposal | A reviewable, atomic set of architecture operations |
| Decision | An architectural decision governing one or more elements |
| Constraint | A named, inheritable obligation on elements |
| WorkItem | A node in the work containment tree |
| AcceptanceCriterion | A verifiable condition owned by a Task |
| Repository | An implementation projection of one or more Components |
| ImplementationMapping | `Repository implements Component` |
| WorkPackageProfile | The context-construction policy for a package |
| WorkPackage | The immutable, runtime-neutral execution contract |
| ExecutionRun | One attempt to fulfil a WorkPackage |
| RuntimeAdapter | A translator between WorkPackage and a concrete runtime |
| AgentRole | A vendor-neutral label for how a runtime is configured (ACL) |
| Alignment | Agreement between Nexus state and repository projections |
| Drift | Detected disagreement |

### 4.2 Containment and provision

**Containment** (structural, single-parent, immutable in shape):

| Parent kind | Child kind |
|---|---|
| product | domain |
| domain | subsystem |
| subsystem | **component** |
| subsystem | **capability** |
| initiative | epic |
| epic | feature |
| feature | task |

Root kinds — `product`, `initiative` — have no parent, enforced by a check
rather than a table row.

**Provision** (behavioural, many-to-many, mutable):

```
Component --provides--> Capability      (0..n providers per capability)
                                        (at most one marked primary)
```

Why this split (R2). Capability is where Work meets Architecture, so its
identity must be at least as stable as the work referencing it. Components are
the churniest layer of the taxonomy — split, merged, replaced. Under v1's
`component contains capability`:

- governance inherits down containment, so moving a capability silently changed
  the resolved constraint set for unrelated Tasks, breaking the determinism
  claim of §11.1 for reasons unconnected to the task;
- retiring a component structurally orphaned its capabilities;
- multi-provider capabilities were inexpressible, although
  `WORK_PACKAGE_SPEC.md` already declares `components:` as an array;
- `parent_id` carried two different edge types, so `ancestry` and `impactOf`
  walked a provision edge as though it were containment.

The Constitution's own Graph Model states the relation as `Component provides
Capability` — *provides*, not *contains*. v1 collapsed the two; v2 separates
them.

A capability with zero providers is no longer a broken tree node. It is a
meaningful, queryable state: **unimplemented** (§8.5).

### 4.3 Relations (canonical)

```
Product        contains       Domain
Domain         contains       Subsystem
Subsystem      contains       Component
Subsystem      contains       Capability
Component      provides       Capability        (many-to-many, primary flag)
Component      dependsOn      Component
Repository     implements     Component         (primary flag)
Task           affects        Capability
Task           implementedIn  Repository        (override only)
Repository     anchors        ArchitectureElement   (§13, under review)
Decision       governs        ArchitectureElement
Constraint     constrains     ArchitectureElement
Element        supersededBy   Element           (via succession, many-to-many)
Proposal       mints          Element
Proposal       retires        Element
```

**Repository resolution order** for `Task → Repository`:
1. explicit `implementedIn` override on the Task, if any;
2. otherwise the component's **primary** repository;
3. otherwise all mapped repositories, and the generation gate refuses if the
   profile forbids ambiguity.

The override exists so that step 3 is rare rather than routine. It is the one
Work → Repository reference in the model, and §2.3 declares it legal for that
purpose only.

### 4.4 What is core, and what is not

`AGENT_RUNTIME_MODEL.md` states that roles belong to Nexus. v1 read that as
"AgentRole is a core domain identifier". v2 reads it more narrowly and, we
think, correctly: roles belong to Nexus in the sense of **not belonging to a
vendor**. That is a requirement on the ACL's vocabulary, not a claim that Role
is a core aggregate.

The test is behavioural. In the whole of v1, the core domain used a role for
exactly one thing: selecting an adapter. Adapter selection is a Runtime
Integration concern. The role table had no core invariant and no core
behaviour.

| Concept | Home | Why |
|---|---|---|
| `WorkPackageProfile` (`wpp.*`) | **core**, Execution | governs context construction, which the Constitution assigns to the platform; has invariants and behaviour |
| `AgentRole` (`role.*`) | **ACL**, Runtime Integration | a neutral label used to configure a runtime; no core behaviour |

The practical argument: a core `agent_role` table is a **leak attractor**. It
is where `max_turns`, `subagent_type` and `model` would land in six months,
each individually reasonable and collectively a vendor concept in the core
model. Moving it to `runtime` leaves those columns nowhere to go.

The neutral role vocabulary is preserved in full — `role.task-analyst`,
`role.context-navigator`, `role.code-locator`, `role.implementer`,
`role.knowledge-maintainer`, `role.consistency-auditor` — in the context that
uses it.

## 5. Architecture Evolution

The mechanism v1 lacked entirely.

### 5.1 Why this is in the MVP

v1 had no path for a Task requiring new architecture. A Task cannot leave
`draft` without a Capability link; Capabilities may only originate in Nexus;
agents never write to Nexus; MCP write tools were postponed. So "implement
invoice discounts, which needs a new `comp.discount-engine`" had nowhere to go
— and that is the ordinary case in delivery, not an edge case.

The workaround under delivery pressure is to create the component in the
repository and register it in Nexus afterwards: architecture originating in a
projection, the precise breach the platform exists to prevent. An unspecified
evolution path is not a coverage gap; it is an active incentive to violate the
Constitution.

### 5.2 Architecture change is itself governed work

> A proposal is to architecture what a pull request is to code.

GitHub governs code merge. Nexus governs architecture merge. The platform
already had a review-and-approve model; v2 applies it to the platform's own
state.

```
ArchitectureChangeProposal
  id           acp.<ulid>
  intent       short statement
  state        draft → proposed → approved → applied | rejected
  authoredBy   opaque principal ('human:<id>' | 'run:<id>')
  approvedBy   human principal
  operations   ordered ArchitectureOperation[]
```

```
ArchitectureOperation
  op                  create | retire
  targetId            (retire)
  mintId, mintKind, mintParentId, mintName   (create)
  supersedesId        (create, optional — records succession)
  requiresRepository  (create, kind=component)
```

`authoredBy` is a deliberately opaque string rather than a foreign key: an FK
to `execution.execution_run` would point Architecture → Execution, against
§2.3.

### 5.3 Operations in scope

| Op | MVP | Note |
|---|---|---|
| create | **yes** | without it the deadlock stands |
| retire | **yes** | needed for any real change |
| provide | **yes** | added Iteration 12 — `create` alone mints an element but does not make it *usable*: a component minted to satisfy a missing capability still failed `buildWorkPackage`'s gate until it also provides that capability. Writes into the existing `element_provision` table (§4.2); no new invariant |
| move | no | reparenting; iteration 2 |
| split | no | iteration 2; **the succession table exists from day one** |
| merge | no | iteration 2 |
| rename | n/a | `name` is mutable — R-4 makes rename a non-event, but no operation writes it yet (Iteration 12 left this disclosed, not fixed) |

### 5.4 The unblocking flow

```
Task authored
→ generation gate refuses: required capability does not exist,
  or a run reports RunBlocked mid-flight
→ draft ArchitectureChangeProposal created by the platform (R-1)
→ Task status → blocked, naming the proposal
→ human reviews, approves in Nexus
→ application, in one transaction:
     mint elements · retire elements · write succession
→ ProposalApplied
     → Repository declared for each minted Component flagged requiresRepository
     → blocked Tasks released for re-gating
→ Repository bootstrap (§10) runs to `active` if a new repository was declared
→ Task links the new capability, returns to ready
→ Work Package generated
```

Two ordering constraints this exposes, both handled by events (§2.2) rather
than by human memory:

- a minted Component that needs a Repository must reach bootstrap `active`
  before an implementation Task can produce a resolvable Work Package;
- `unmappedComponents()` (§8.5) remains the safety net if the
  `requiresRepository` flag was not set.

### 5.5 Succession

`superseded_by` as a single column (v1 §5.1) cannot express a split (1→N) or a
merge (N→1). Succession is a table from iteration 0, even though split and
merge are postponed — retire-plus-create is already a 1:1 succession, and
converting a column to a table after live references exist across an immutable
Work Package history is the expensive kind of migration.

Succession must also be **traversable forward**, so historical identifiers
resolve:

- `resolve(id)` returns the active successor set for any element (§8.4);
- `danglingReferences()` consults succession, so a superseded reference is
  reported as *superseded*, not as *broken*.

### 5.6 Retirement policy

> Retiring an element is refused when live inbound references exist from
> non-terminal Work Items or `active` Repositories, unless the same proposal
> supplies a succession edge.

This is the invariant that approval checks. Immutable Work Packages are
explicitly **not** live references — they are historical records and must
survive retirement of everything they name (R-3).

## 6. Stable ID Strategy

### 6.1 Two ID classes

**Authored IDs** — human-meaningful, slug-based, immutable, referenced across
contexts and inside repositories.

```
<prefix>.<slug>
slug := [a-z0-9]+(-[a-z0-9]+)*
```

| Prefix | Entity | Context |
|---|---|---|
| `prod.` | Product | Architecture |
| `dom.` | Domain | Architecture |
| `subsys.` | Subsystem | Architecture |
| `comp.` | Component | Architecture |
| `cap.` | Capability | Architecture |
| `adr.` | Decision | Architecture |
| `con.` | Constraint | Architecture |
| `repo.` | Repository | Repository |
| `init.` | Initiative | Work |
| `epic.` | Epic | Work |
| `feat.` | Feature | Work |
| `task.` | Task | Work |
| `ac.` | AcceptanceCriterion | Work |
| `wpp.` | WorkPackageProfile | Execution |

**Generated IDs** — opaque, machine-minted, never authored.

| Form | Entity |
|---|---|
| `wp.<seq>` | WorkPackage (display form `WP-123`) |
| `run.<ulid>` | ExecutionRun |
| `acp.<ulid>` | ArchitectureChangeProposal |

**Runtime Integration vocabulary** — neutral, but not core (§4.4).

| Prefix | Entity | Context |
|---|---|---|
| `role.` | AgentRole | Runtime Integration |

Internal-only entities — provision rows, mapping rows, operations, anchors —
use surrogate UUIDs and get **no** public identifier. Only what crosses a
context boundary earns a stable ID.

### 6.2 Rules

1. IDs are globally unique on the full string, including prefix.
2. IDs are immutable. `name` is mutable; `id` never is.
3. Slugs are flat, not path-qualified, keeping deterministic retrieval a single
   lookup.
4. Nothing is deleted. `status` moves `active → deprecated → retired`.
5. Replacement is succession (§5.5), never ID reuse.
6. A retired ID is never reissued.
7. Nexus mints every ID — GitHub, Jira and runtimes never do.
8. Every ID is minted either by an authoring API call or by an applied
   proposal. There is no third path.

### 6.3 Postponed

Path-qualified slugs, ID aliasing, multi-tenant namespacing. All additive.

## 7. Relational Schema

Postgres is the system of truth. One schema per bounded context.

### 7.1 Cross-context foreign keys

R-3 applied. This table is the authority; the DDL below implements it.

| Reference | FK? | Reason |
|---|---|---|
| `work.work_item_capability.capability_id` | **yes** | live; bears the no-orphan-task invariant |
| `work.work_item_repository.repository_id` | **yes** | live; override edge, direction declared in §2.3 |
| `work.work_item.blocked_by_proposal_id` | **yes** | live; Work → Architecture |
| `repo.repository_component.component_id` | **yes** | live; bears the mapping invariant |
| `repo.file_anchor.element_id` | **yes** | live (pending §13) |
| `execution.execution_run.proposal_id` | **yes** | live; proposals are never deleted, only terminated |
| `execution.work_package.task_id` | **no** | historical; must survive task retirement |
| IDs inside `execution.work_package.payload` | **no** | historical, immutable |
| `execution.execution_run.adapter_id` | **no** | crosses the Runtime Integration ACL |
| `architecture.change_proposal.authored_by` | **no** | opaque provenance; an FK would invert §2.3 |

The three live non-FK references are compensated by named Alignment queries
(§8.5), as R-3 requires.

### 7.2 Kind-checked references without triggers

An FK to `element(id)` does not stop a Task from affecting a `subsystem`. A
composite unique key plus a constant-defaulted, checked column makes kind
enforcement fully declarative:

```sql
alter table architecture.element
  add constraint element_id_kind_uq unique (id, kind);
-- redundant for uniqueness (id is the PK), required as an FK target
```

This pattern replaces v1's `element_dependency` and provision triggers. Only
the legal-containment check remains a trigger, because it is a two-column
lookup against a table.

### 7.3 `architecture`

```sql
create table architecture.element (
  id         text primary key
               check (id ~ '^(prod|dom|subsys|comp|cap)\.[a-z0-9]+(-[a-z0-9]+)*$'),
  kind       text not null check (kind in
               ('product','domain','subsystem','component','capability')),
  parent_id  text references architecture.element(id),
  name       text not null,
  status     text not null default 'active'
               check (status in ('active','deprecated','retired')),
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now(),
  constraint element_root_parent
    check ((parent_id is null) = (kind = 'product')),
  constraint element_id_kind_uq unique (id, kind)
);

create table architecture.legal_containment (
  parent_kind text,
  child_kind  text,
  primary key (parent_kind, child_kind)
);
-- rows: (product,domain) (domain,subsystem) (subsystem,component) (subsystem,capability)
-- trigger on element enforces (parent.kind, kind) ∈ legal_containment

create table architecture.element_provision (          -- Component provides Capability
  component_id    text not null,
  component_kind  text not null default 'component'
                    check (component_kind = 'component'),
  capability_id   text not null,
  capability_kind text not null default 'capability'
                    check (capability_kind = 'capability'),
  is_primary      boolean not null default false,
  primary key (component_id, capability_id),
  foreign key (component_id, component_kind)
    references architecture.element (id, kind),
  foreign key (capability_id, capability_kind)
    references architecture.element (id, kind)
);

create unique index element_provision_primary_uq
  on architecture.element_provision (capability_id) where is_primary;

create table architecture.element_dependency (
  from_id   text not null,
  from_kind text not null default 'component' check (from_kind = 'component'),
  to_id     text not null,
  to_kind   text not null default 'component' check (to_kind = 'component'),
  primary key (from_id, to_id),
  check (from_id <> to_id),
  foreign key (from_id, from_kind) references architecture.element (id, kind),
  foreign key (to_id,   to_kind)   references architecture.element (id, kind)
);

create table architecture.change_proposal (
  id          text primary key,                  -- acp.<ulid>
  intent      text not null,
  state       text not null default 'draft'
                check (state in ('draft','proposed','approved','applied','rejected')),
  authored_by text not null,                     -- opaque: 'human:<id>' | 'run:<id>'
  approved_by text,
  created_at  timestamptz not null default now(),
  applied_at  timestamptz,
  check ((state = 'applied') = (applied_at is not null)),
  check (state not in ('approved','applied') or approved_by is not null)
);

create table architecture.change_operation (
  id                    uuid primary key default gen_random_uuid(),
  proposal_id           text not null references architecture.change_proposal(id),
  ordinal               int  not null,
  op                    text not null check (op in ('create','retire','provide')),
  target_id             text references architecture.element(id),      -- retire
  mint_id               text,                                          -- create
  mint_kind             text,
  mint_parent_id        text references architecture.element(id),
  mint_name             text,
  supersedes_id         text references architecture.element(id),
  requires_repository   boolean not null default false,
  provide_component_id  text,      -- provide; no FK — may name a mint_id from
  provide_capability_id text,      -- earlier in the same proposal, not yet committed
  provide_is_primary    boolean not null default false,
  unique (proposal_id, ordinal),
  check (case op when 'retire'  then target_id is not null
                 when 'create'  then mint_id is not null
                                 and mint_kind is not null
                                 and mint_name is not null
                 when 'provide' then provide_component_id is not null
                                 and provide_capability_id is not null end)
);
-- provide (Iteration 12) writes into the existing element_provision table
-- (§4.2) unchanged; that table's own kind-checked FKs are the final word,
```

## 8. Graph Schema

### 8.1 MVP decision: no graph database

The graph is the canonical relationship model, not necessarily a separate
store. In the MVP it is a set of named recursive-CTE views over Postgres. Node
labels, edge types and traversal names are fixed now so that adopting a graph
database later is a substitution, not a redesign.

### 8.2 Node labels

`Product`, `Domain`, `Subsystem`, `Component`, `Capability`,
`Initiative`, `Epic`, `Feature`, `Task`,
`Repository`, `Decision`, `Constraint`

Node key: the stable ID. Node properties: `name`, `status`.

Not graph nodes — reached by ID from a node: `AcceptanceCriterion`,
`FileAnchor`, `WorkPackage`, `ExecutionRun`, `ArchitectureChangeProposal`. A
proposal is a change record, not a structural node; its *effects* appear in the
graph as minted nodes, status changes and `SUPERSEDED_BY` edges.

### 8.3 Edge types

| Edge | From → To | Backing table |
|---|---|---|
| `CONTAINS` | Product→Domain→Subsystem→{Component, Capability}; Initiative→Epic→Feature→Task | `parent_id` |
| `PROVIDES` | Component → Capability | `element_provision` |
| `DEPENDS_ON` | Component → Component | `element_dependency` |
| `IMPLEMENTS` | Repository → Component | `repository_component` |
| `AFFECTS` | Task → Capability | `work_item_capability` |
| `IMPLEMENTED_IN` | Task → Repository (override) | `work_item_repository` |
| `ANCHORS` | Repository → Element | `file_anchor` (§13) |
| `GOVERNS` | Decision → Element | `decision_scope` |
| `CONSTRAINS` | Constraint → Element | `element_constraint` |
| `SUPERSEDED_BY` | Element → Element | `element_succession` |

### 8.4 Named traversals

These names are the retrieval contract. MCP tools and the Context Builder call
only these — never ad-hoc queries, never document search.

| Traversal | Path |
|---|---|
| `ancestry(element)` | element →CONTAINS*→ root |
| `providersOf(capability)` | Capability ←PROVIDES← Component |
| `capabilitiesOf(component)` | Component →PROVIDES→ Capability |
| `implementationPath(task)` | Task→AFFECTS→Capability←PROVIDES←Component←IMPLEMENTS←Repository |
| `impactOf(component, depth)` | Component→DEPENDS_ON{1..depth}→Component |
| `governanceOf(element)` | ancestry(element) ←GOVERNS/CONSTRAINS← Decision/Constraint |
| `localSubgraph(component)` | Component + provided capabilities + direct dependencies |
| `resolve(id)` | element →SUPERSEDED_BY*→ active successor set |

`implementationPath` is now legitimately multi-valued at the Component step
(§4.2). The repository step is disambiguated by §4.3's resolution order.

`governanceOf` for a Work Package is the **union**
`ancestry(capability) ∪ ancestry(each providing component)`, nearest-ancestor
wins on conflict. Governance therefore no longer moves when provision changes.

### 8.5 Alignment queries

The Alignment context's entire surface.

| Query | Detects | Role |
|---|---|---|
| `orphanTasks()` | Task with no `AFFECTS` | constitutional invariant |
| `unprovidedCapabilities()` | Capability with no provider | **new in v2** — the state that replaced v1's orphaned tree node |
| `unmappedComponents()` | Component with no inbound `IMPLEMENTS` | safety net for §5.4 |
| `danglingReferences()` | edge endpoint missing or `retired`, **succession-aware** | reports superseded vs broken |
| `dependencyCycles()` | `DEPENDS_ON` cycles | deferred aggregate invariant |
| `unknownAdapters()` | `execution_run.adapter_id` with no registration | **compensates a live non-FK reference (R-3)** |
| `staleWorkItemReferences()` | blocked Task whose proposal is `rejected` | compensates the blocked-flow edge case |
| `repositoryProjectionDrift()` | managed-region hash mismatch | §10.5 |

### 8.6 Inheritance semantics

Constraints and Decisions inherit **down** `CONTAINS` only. Resolution is
nearest-ancestor-wins, and the resolved set is materialised into the Work
Package so the agent never re-derives it.

Because Capability now hangs from Subsystem, a Decision on `dom.billing`
reaches both the Components beneath it and the Capabilities beneath it, by the
same rule, without either depending on provision.

## 9. MCP Specifications

### 9.1 Role of MCP

- The Work Package delivers the **minimum** context required to start.
- MCP delivers **deterministic expansion** during a run.
- MCPs are read views over Postgres. They cache nothing. They are not systems
  of truth.
- No free-text or semantic search. Every tool takes IDs and returns structure.
- **All MCP tools are read-only in the MVP** (R-1).

Three servers, matching the Constitution.

### 9.2 Architecture MCP

| Tool | Input | Output |
|---|---|---|
| `architecture.get_element` | `id` | kind, name, status, parentId, childIds |
| `architecture.get_ancestry` | `id` | ordered ancestor IDs with kinds |
| `architecture.get_providers` | `capabilityId` | component IDs, primary flagged |
| `architecture.get_capabilities` | `componentId` | capability IDs, primary flagged |
| `architecture.get_dependencies` | `componentId`, `direction`, `depth≤3` | component IDs by distance |
| `architecture.get_governance` | `elementId` | resolved decisions + constraints |
| `architecture.resolve` | `id` | active successor set, or self |

`get_providers` and `resolve` are new in v2 and are the tools that make
provision and succession usable at runtime.

### 9.3 Work MCP

| Tool | Input | Output |
|---|---|---|
| `work.get_item` | `id` | kind, title, status, parentId, childIds |
| `work.get_task_context` | `taskId` | title, ACs, affected capability IDs, feature ID |
| `work.list_tasks` | `featureId`, `status?` | task IDs |

### 9.4 Repository MCP

| Tool | Input | Output |
|---|---|---|
| `repo.get_repository` | `id` | provider ref, branch, implemented component IDs |
| `repo.list_for_component` | `componentId` | repository IDs, primary flagged |
| `repo.get_anchors` | `repositoryId`, `elementId?` | path globs + element IDs (§13) |
| `repo.get_bootstrap_manifest` | `repositoryId` | expected generated files + region hashes |

### 9.5 Access model

Every MCP session is authorised by a **run-scoped grant** issued when an
ExecutionRun is dispatched:

```
grant = {
  runId,
  workPackageId,
  allowedElementIds,      -- WP elements ∪ impactOf(components, context_depth + 1)
  allowedRepositoryIds,
  expiresAt
}
```

The grant is always **exactly one level wider** than the package the profile
built (§11.2). That is a rule, not two magic numbers: the package carries the
minimum to start, the grant carries the minimum to *discover what else is
needed*, and anything beyond that is a `RunBlocked` with reason
`context-insufficient` rather than a silent widening.

A tool call outside the grant is refused. Authorisation is therefore a property
of the graph rather than of a role table, which removes the need for RBAC in
the MVP and bounds agent blast radius provably.

### 9.6 Postponed

Write tools — which, when they arrive, may only create draft proposals or
append observations (R-1) — subscriptions, pagination beyond a fixed cap, and
a fourth Execution MCP.

## 10. Repository Bootstrap

### 10.1 State machine

```
declared → provisioned → mapped → bootstrapped → active
```

### 10.2 Steps

| # | Step | Precondition | Effect |
|---|---|---|---|
| 1 | Component exists | `comp.*` is `active` | — |
| 2 | Declare Repository | — | Nexus mints `repo.<slug>`; state `declared` |
| 3 | Provision | — | `VcsProvider.create()`; store `provider_ref`; state `provisioned` |
| 4 | Register mapping | ≥1 component | `IMPLEMENTS` edge, primary flag; state `mapped` |
| 5 | Generate projection | mapped | files rendered; branch `nexus/bootstrap`; PR opened; state `bootstrapped` |
| 6 | Human merges PR | CI green | state `active`; `RepositoryActivated` |

Step 2 may be triggered by `ProposalApplied` (§5.4) rather than by hand.
Repositories are never created outside this flow. `VcsProvider` is a port;
GitHub is one adapter.

### 10.3 Generated artifacts

| File | Content | Authority |
|---|---|---|
| `.nexus/repository.json` | repo ID, component IDs, Nexus base URL, schema version, region hashes | projection |
| `.nexus/architecture.snapshot.json` | `localSubgraph(component)` | projection |
| `.github/workflows/nexus-alignment.yml` | drift check job | projection |
| `CLAUDE.md`, `AGENTS.md` | runtime hint files rendered from `runtime.hint_file_template` | projection |

Nothing in a repository may introduce an element, mapping or capability absent
from Nexus. That is the guardrail keeping architecture from originating in a
projection — and §5 is what makes obeying it practical.

### 10.4 Managed regions

Generation is a pure function:

```
render(repository, localSubgraph, templateVersion) → managed regions
```

v1 claimed drift detection came free from regenerate-and-diff. It does not
survive the first human edit of a generated file, and `CLAUDE.md` will be
edited — after which the diff is permanently noisy and the check gets ignored,
which is worse than having no check.

So generated content is bounded by explicit markers:

```
<!-- nexus:begin generated · do not edit -->
...
<!-- nexus:end generated -->
```

Only the managed region is hashed (`repo.generated_region`) and only the
managed region is compared. Outside the markers, humans own the file.

### 10.5 Alignment check (CI)

The workflow posts `.nexus/repository.json` to `POST /alignment/verify`.

Fails when:
- repository ID unknown
- `implements` mapping missing or contradicted
- a referenced element ID does not exist **and has no succession** (§5.5)
- a referenced element is `retired` with no successor
- a mapped component **provides** no capabilities

Warns when:
- a referenced element is superseded — reported with its successor
- the snapshot hash is stale (Nexus moved ahead)
- a managed region differs from a fresh render

### 10.6 Postponed

Anchor verification (§13), dependency-cycle enforcement, capability coverage by
tests.

## 11. Work Package Generation

### 11.1 Contract

```
buildWorkPackage(taskId, profileId) → WorkPackage
```

Pure with respect to graph state. Same graph + same task + same profile ⇒ same
content hash ⇒ the existing immutable package is returned. Generation is
idempotent and auditable.

Because provision is no longer containment (§4.2), resolved governance no
longer changes when a capability's provider changes — which is what makes this
determinism claim true rather than merely stated.

MVP ships one profile: `wpp.implementation`, `context_depth = 0`.

### 11.2 Pipeline

1. **Gate.** Fail closed unless: Task exists and is `ready`; ≥1 `AFFECTS`; ≥1
   AcceptanceCriterion; every affected capability has ≥1 provider; every
   resolved component has a repository resolvable per §4.3; no referenced
   element is `retired` without succession.
   A gate failure that is *missing architecture* initiates §5.4 rather than
   returning an error to the caller.
2. **Resolve succession.** Any referenced ID is normalised through `resolve()`
   before traversal.
3. **Traverse.** `implementationPath(task)` → capabilities → providing
   components (primary only, unless `include_all_providers`) → repositories
   (§4.3 order).
4. **Bound.** `impactOf(components, profile.context_depth)`. Default 0.
5. **Anchor.** Per repository, anchors filtered to resolved elements → file
   globs (§13).
6. **Govern.** `governanceOf` over the union of capabilities and providing
   components; nearest-ancestor wins.
7. **Frame.** Parent Feature ID and title only. No prose inherited upward.
8. **Canonicalise.** Sort keys, sort arrays, serialise, hash.
9. **Persist.** Insert-only. Emit `WorkPackageIssued`.

Depth lives in the profile (R9), so widening context is configuration rather
than a code change — and §9.5 keeps the grant one level ahead of it
automatically.

### 11.3 Payload

Exactly `WORK_PACKAGE_SPEC.md`, plus `schemaVersion` and `profile`.

```yaml
id: WP-123
schemaVersion: 2
profile: wpp.implementation
task: task.invoice-discount-validation
feature: feat.invoice-discounts
capabilities: [cap.invoice-discount]
components: [comp.invoice-service]
repositories: [repo.billing-service]
files: [InvoiceService.java]
constraints: [con.backward-compatible]
acceptanceCriteria: [ac.discount-applied, ac.existing-behaviour-unchanged]
decisions: [adr.discount-strategy-v1]
```

IDs, not prose. Statements for `acceptanceCriteria`, `constraints` and
`decisions` are fetched through MCP when needed, keeping the package small and
the platform the single source of the text.

`components` and `repositories` may now legitimately hold more than one entry,
which is what the spec's array shape always anticipated.

`files` is retained pending §13.

### 11.4 Postponed

Token budgeting, relevance ranking, multi-task packages, additional profiles.
Explicitly excluded: embedding or vector retrieval — retrieval stays
deterministic.

## 12. Agent Orchestration

### 12.1 Layering

```
Execution context (core, runtime-agnostic)
  ├─ WorkPackageProfile registry
  ├─ Context Builder            (§11)
  ├─ Orchestrator               (run lifecycle, policy, grants)
  └─ AgentRuntimeAdapter        (port)
        │
Runtime Integration context (ACL)
  ├─ AgentRole vocabulary + adapter/role matching
  └─ Claude SDK Adapter         (the only runtime-aware code in the system)
        │
Agent Runtime
```

### 12.2 The port

```
interface AgentRuntimeAdapter {
  id: AdapterId
  capabilities(): AdapterCapabilities        // supported roles, streaming, tools
  start(run, workPackage, mcpGrant): AdapterHandle
  events(handle): stream<RunEvent>
  cancel(handle): void
}
```

Runtime-neutral event vocabulary — the full set, six in v2:

`RunStarted`, `ContextRequested`, `ArtifactProduced`, **`RunBlocked`**,
`RunFailed`, `RunCompleted`

```
RunBlocked {
  reason: architecture-change-required | mapping-missing | context-insufficient
  proposalDraft?: { intent, operations[] }
}
```

v1's five-event vocabulary was incomplete. A run that discovers mid-flight that
architecture must change had only `RunFailed` available, which is wrong twice
over: "blocked on platform-owned state" is a different outcome from "failed",
and it is the outcome that should *produce a proposal*. Without it, a blocked
run degrades into a repository-side workaround — the §5.1 breach.

No messages, tokens, tool-call shapes or model names cross this boundary.
Anything a runtime emits that does not map to these six is the adapter's
problem.

### 12.3 Run lifecycle

```
pending → dispatched → running → produced → completed
                              ↘ blocked
                              ↘ failed
                              ↘ cancelled
```

`blocked` is **terminal for the run**. Resolution happens through the proposal
flow (§5.4), and a fresh run is dispatched afterwards against a newly generated
Work Package — runs are never resumed across an architecture change, because
the package they were built from is no longer the current truth.

### 12.4 The Orchestrator

1. resolves the Work Package and its profile
2. asks Runtime Integration for an enabled adapter supporting the desired role
3. issues the run-scoped MCP grant (§9.5)
4. dispatches, records `RunEvent`s, drives the state machine
5. on `ArtifactProduced`, records `artifact_ref`
6. on `RunBlocked`, raises the `RunBlocked` domain event — Architecture drafts
   the proposal, Work blocks the Task (§2.2)

The Orchestrator holds no runtime knowledge and writes no aggregate outside
Execution.

### 12.5 Output path

Agents do not write to Nexus (R-1). An ExecutionRun produces a **branch and a
pull request**; GitHub remains merge governance; a human merges.

This single constraint removes agent write authorisation, optimistic
concurrency on the graph, and rollback machinery from the MVP. `RunBlocked` is
what makes it survivable: the agent has a legitimate way to say "the platform's
model is wrong" without needing write access to fix it itself.

### 12.6 Roles in the MVP

The `role.*` vocabulary lives in Runtime Integration (§4.4). What the MVP
actually orchestrates:

| Role | MVP treatment |
|---|---|
| `role.implementer` | **orchestrated**, paired with `wpp.implementation` |
| `role.task-analyst` | collapses into the §11.2 gate |
| `role.context-navigator` | collapses into MCP — the agent navigates itself |
| `role.code-locator` | collapses into anchors + Repository MCP (§13) |
| `role.knowledge-maintainer` | registered, not orchestrated; awaits Observations (§15) |
| `role.consistency-auditor` | replaced by Alignment (§8.5, §10.5) |

One role, one run, no choreography.

### 12.7 Claude SDK Adapter

Translates only:
- WorkPackage + role → system prompt, from `runtime.adapter_registration.config`
- MCP grant → MCP server configuration and tool allowlist
- SDK events → the six `RunEvent` kinds
- final state → branch push + PR via `VcsProvider`

Adding a second runtime means one `adapter_registration` row, one
`adapter_role_support` set and one class. If that ever requires a change to
§2–§8, this design failed its own test.

## 13. Open Design Question — file-level context

**Status: unresolved. Not decided in v2.** R12 was deliberately excluded from
the accepted set. The MVP proceeds with Alternative A so that the rest of this
document is implementable, and this section exists so the choice is made on
evidence rather than by default.

### 13.1 The question

Should Nexus hold file-level knowledge at all, and if so, in what form?

`WORK_PACKAGE_SPEC.md` mandates a `files:` field on the Work Package. The
Constitution assigns source code to repositories and forbids Nexus owning
implementation detail. A file path stored in Nexus is a projection detail
leaking upward into the system of truth. Both statements are authoritative, and
they pull in opposite directions.

### 13.2 What is actually at risk

Not precision — **maintenance**. The likely failure of hand-curated anchors is
not that globs are too coarse but that nobody updates them. If anchors rot,
`files:` becomes vestigial: agents ignore it and search the repository anyway,
and the platform carries a table that misleads.

### 13.3 Alternatives

**A — Curated FileAnchors in Nexus** *(current MVP position)*

Humans maintain path globs per repository, bound to elements.

- Assumes: anchors are few, stable, and worth curating.
- Constitutional pressure: Nexus holds implementation detail.
- Cost: low to build; ongoing human maintenance.
- Failure mode: silent rot; `files:` misleads rather than helps.
- Spec impact: none — satisfies `files:` as written.

**B — Derive at dispatch**

Nexus stores nothing. The adapter or Repository MCP computes file hints from
the repository at dispatch time (conventions, module layout, VCS history).

- Assumes: a cheap, deterministic-enough derivation exists per ecosystem.
- Constitutional pressure: none — implementation detail stays in the projection.
- Cost: per-ecosystem derivation logic; determinism of the Work Package hash
  becomes conditional on repository state, not just graph state.
- Failure mode: `buildWorkPackage` stops being a pure function of the graph,
  which weakens §11.1.
- Spec impact: `files:` becomes adapter-populated, not Nexus-populated.

**C — Machine-maintained file graph**

`Repository contains File` as real nodes, indexed by CI on every merge.

- Assumes: index churn is affordable and the graph stays queryable.
- Constitutional pressure: large volume of implementation detail in the system
  of truth, though machine-maintained rather than curated.
- Cost: highest — indexer, write path, retention, and the graph grows by orders
  of magnitude.
- Failure mode: the file graph becomes the largest thing in the platform and
  the least useful.
- Spec impact: none.

**D — Drop file-level context entirely**

`files:` is emptied or removed. The agent locates code within its repo-scoped
grant.

- Assumes: modern runtimes locate code well enough unaided.
- Constitutional pressure: none — the cleanest separation.
- Cost: lowest; delete a table.
- Failure mode: larger, slower runs; possibly worse localisation on big repos.
- Spec impact: requires amending `WORK_PACKAGE_SPEC.md`.

**E — Conventions, not paths**

Nexus stores per-component *conventions* (module path patterns, language,
layout profile) rather than file paths. The runtime expands them locally.

- Assumes: conventions are stable where paths are not.
- Constitutional pressure: mild — a convention is architecture-adjacent, and
  arguably belongs to the Component.
- Cost: moderate; a small vocabulary of layout profiles.
- Failure mode: conventions drift from reality as quietly as anchors do, with
  less obvious symptoms.
- Spec impact: `files:` becomes a derived expansion of a stored pattern.

### 13.4 What would settle it

Deliberately not decided here. The evidence to collect during iteration 1:

1. After ten real Work Packages, how many `files:` entries were still correct?
2. Did any human update an anchor without being asked?
3. Did runs that ignored `files:` produce worse pull requests than runs that
   used it?
4. How large is the localisation cost on the largest real repository?

If (1) is low and (2) is zero, A is dead and the choice is between B, D and E.
If (3) shows no difference, D wins on cost alone. C should be adopted only if
(4) proves prohibitive, since it is the most expensive option by a wide margin.

### 13.5 Consequences of leaving this open

Contained. `file_anchor` is one table, `ANCHORS` one edge, `repo.get_anchors`
one tool, and `files:` one payload field. Every alternative removes or replaces
exactly those four. Nothing else in this document depends on the outcome.

Acceptance criterion for this architecture: **iteration 1f closes without a
change to §2–§8.**

A note on §4.2's claim that containment is data. It is half true, and v1
overstated it. The containment *rules* are a table, but the *kind vocabulary*
is baked into `element.kind`'s check constraint, the ID prefix table (§6.1) and
the traversal names (§8.4). Adding a taxonomy level touches all three. The
first pressure will likely be a Component inside a Component; the current model
forbids it, and that is a deliberate limit rather than an oversight.
